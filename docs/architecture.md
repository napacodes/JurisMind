# JurisMind architecture

## Current foundation

JurisMind uses a modular monolith in an npm workspaces/Turborepo repository. `apps/web` is a Next.js App Router application and `apps/api` is a NestJS REST API. Shared packages belong in `packages/*` only when code is genuinely reused and can have a clear typed boundary. Business rules belong in API modules, not page components or controllers.

The web app communicates with the API over HTTP. The API is the authority for identity, authorization, validation, and access to legal and tenant data. The API exposes a versionable REST surface under `/api`; OpenAPI documentation will be added alongside API contracts.

## Identity and authorization foundation (Milestone 4, Phase 1)

`apps/api/prisma/schema.prisma` defines identity and practice-workspace persistence. Users are global identities; practice memberships connect them to either a firm or an individual-practice workspace and carry practice-scoped roles. Platform Super Admin grants are a separate relation and do not create practice memberships or confer ordinary practice access. A Super Admin's platform duties must be explicitly authorized by server policy and audited. Firm Admin, Lawyer, and Assistant permissions apply only within the active workspace membership; a Firm Admin cannot grant themselves platform privileges. The database model does not itself constitute a complete authorization implementation.

A firm can have multiple active lawyer memberships. An individual-practice workspace has exactly one active lawyer membership, exactly one active primary lawyer profile, and may have assistants. A deferred PostgreSQL constraint trigger checks the profile invariant at commit, allowing the workspace, membership, and profile to be created together in one transaction. The additive migration backfills only individual workspaces with exactly one active lawyer profile; it aborts rather than guessing when an existing workspace has zero or multiple candidates. A partial unique index prevents multiple primary profiles per workspace.

Assistants have one optional `supervisingLawyerMembershipId` at a time, and its composite foreign key keeps that relation within the same workspace. Database checks/triggers require active assistants to reference an active Lawyer membership, and prevent changing the supervisor membership's role/status while assigned assistants depend on it. Invited or suspended assistants may have no active assignment. An assistant cannot be made active without one. The current relation is the source of truth for future inherited access: matter authorization must evaluate it live and must not persist stale access grants from a previous supervisor.

The schema does not authorize reassignment actors or require a matching audit row. The membership API authorizes assignment changes against active workspace membership/role and writes success audit events atomically with the reassignment. No matter grant/cache model exists yet, so no inherited matter access is created or revoked; future matter authorization must evaluate the current assignment live. Public registration must never create `PlatformRoleGrant` records; platform grants remain restricted to an explicitly authorized and audited platform administration path.

`LawyerProfile` is one-to-one with a lawyer membership and workspace-scoped. An individual workspace has exactly one active primary profile; firms cannot mark a profile as primary. A firm membership does not imply access to another lawyer's private matters: future matter records need an explicit owner/assignment or permission relationship, and every API query must enforce it. Matter permissions and ethical walls remain unresolved and are not implied by this foundation.

Sessions store only a unique lowercase SHA-256 token hash, never a browser bearer token. This is suitable only for high-entropy opaque tokens (at least 256 random bits); low-entropy tokens must not be stored as plain SHA-256 hashes. Phase 2 implements Argon2id password hashing and backend-managed cookie sessions through the API. Audit events intentionally store event metadata and references only; do not put document content, credentials, session tokens, or other privileged legal data in metadata.

### Authentication and session management (Milestone 4, Phase 2)

The API exposes audience-specific `POST /api/auth/login/administration`, `/firm`, `/lawyer`, and `/assistant`, plus `POST /api/auth/logout` and `GET /api/auth/me`. Each login path applies server-side eligibility against an active Super Admin grant or the matching active workspace membership (assistants also require their active supervising lawyer). A correct password alone never crosses account types. Sessions and MFA challenges store the server-selected audience; the session guard filters platform grants or practice memberships to that audience before protected APIs authorize the request. Legacy sessions and pending MFA challenges without an audience were revoked/consumed by the additive migration and require sign-in again. Audience is not taken from a request body or redirect. Login returns a generic invalid-credentials response. Workspace invitation creation and authenticated acceptance are implemented separately. Login creates a 256-bit random opaque token, persists only its SHA-256 hash, and sends the token only in an HttpOnly cookie. The API checks session expiry, revocation, and account status on each current-user request and updates last-seen time. Logout revokes the server record and clears the cookie.

The dedicated `/login` page offers firm and lawyer entry points; `/administration/login` remains a separate platform operator route. The database continues to use one global user identity and separate `PlatformRoleGrant` and `PracticeMembership` relations. Dedicated administrator tables are unnecessary: server-side grants provide the platform authorization source of truth, and an active Super Admin grant makes the identity ineligible for all practice login audiences. Session audience also prevents a session from exercising another identity domain. This is an application authorization boundary; PostgreSQL RLS remains unimplemented.

Cookie-authenticated state-changing requests require an exact `Origin` from `TRUSTED_ORIGINS`, and credentialed CORS allows only those configured origins. Preflight permits the current API methods (`GET`, `POST`, `PATCH`) and declared headers, including `Idempotency-Key`. The selected SameSite policy is `Lax`; production uses the `__Host-jurismind_session` name, Secure, and Path `/`, which requires HTTPS and forbids a Domain attribute. Development uses `jurismind_session` over localhost HTTP. Origin validation and SameSite provide defense in depth for current state-changing endpoints; Origin validation alone is not complete CSRF protection. Before broadening cookie-authenticated behavior, add and test a deliberate CSRF design (for example, a token plus Fetch Metadata checks). CORS is not itself an authorization or CSRF boundary.

Required runtime settings are `NODE_ENV`, `DATABASE_URL`, `TRUSTED_ORIGINS`, `SESSION_TTL_SECONDS`, `PASSWORD_MIN_LENGTH`, `LOGIN_RATE_LIMIT_MAX`, and `LOGIN_RATE_LIMIT_WINDOW_SECONDS`; `PORT` defaults to 4000. `TRUSTED_ORIGINS` is a comma-separated exact-origin list with no paths or wildcards. Production origins must be HTTPS. Copy `.env.example` for development and replace its database placeholders locally. Production must supply real secrets and trusted HTTPS origins through the deployment secret manager; the example values are not production credentials.

Login throttling currently tracks failed attempts by normalized identifier and remote IP in process memory. It is useful for a single API process but is reset on restart and is not shared across replicas. A shared rate-limit store or gateway policy is required before relying on it in a multi-instance production deployment. Proxy trust is not enabled; if deployed behind a proxy, configure and validate trusted proxy hops before using forwarded client addresses for rate limiting.

Authentication audit events record successful login, failed login, throttling, and session revocation without credentials, raw tokens, cookies, or request bodies. Failed attempts intentionally omit the submitted email and IP from audit metadata. This is authentication auditing only; it does not implement transactional audits for later authorization or assistant reassignment operations.

### Authorization foundation (Milestone 4, Phase 3)

`AuthorizationContextService` derives an authorization context from the verified session identity and current database rows. It includes only active memberships in active workspaces and non-revoked platform grants. No role, user ID, membership ID, or workspace identifier supplied in a request creates authority. `SessionAuthGuard` runs before `PermissionsGuard`; the permission guard denies routes with missing policy metadata, unknown permission identifiers, missing context, and missing workspace scope. Workspace route parameters identify the requested target only; the user's exact active membership and role are checked against that target.

Initial permission mapping:

| Role | Allowed by this phase |
| --- | --- |
| `FIRM_ADMIN` in a `FIRM` workspace | Read workspace metadata, manage workspace settings, read membership metadata, manage memberships and practice roles, manage all assistant assignments in that firm |
| `LAWYER` in any workspace kind | Read workspace metadata; manage assistant assignments in the workspace, limited to assistants they currently supervise (and assigning unassigned assistants to themselves) |
| `ASSISTANT` in any workspace kind | Read workspace metadata |
| `FIRM_ADMIN` in an `INDIVIDUAL` workspace | No firm-admin permissions |
| Platform `SUPER_ADMIN` | Platform administration only; no implied practice membership or workspace access |

All authenticated users may read their own `/api/auth/me` profile. No current role receives lawyer-private or assistant-authorized matter permissions: matter records, ownership, assignments, and delegation policies do not yet exist. A firm administrator therefore cannot read lawyer-private matters, assistants cannot infer access from their supervisor relationship, and a platform administrator cannot access confidential content through this permission catalogue. These primitives do not constitute complete tenant isolation, matter authorization, or ethical-wall enforcement. Any future protected route must explicitly declare a permission and use transactional, tenant-scoped authorization for writes.

### Practice memberships and assistant relationships (Milestone 4, Phase 4)

`MembershipsModule` exposes these session-protected workspace routes. Every POST/PATCH route also applies the exact trusted-Origin guard:

- `GET /api/workspaces/:workspaceId/memberships` — Firm Admin membership metadata list.
- `POST /api/workspaces/:workspaceId/memberships` — now creates an `INVITED` membership and its secure invitation for an existing active identity, with an explicit practice role. It does not create an identity, accept an invitation, or grant a platform role.
- `PATCH /api/workspaces/:workspaceId/memberships/:membershipId/role` — change an authorized practice role; self-role changes are denied. Active assistants must first be suspended before a role change, clearing the former supervisor relation.
- `POST /api/workspaces/:workspaceId/memberships/:membershipId/suspend` and `/reinstate` — Firm Admin membership lifecycle operations. Suspending an assistant clears its supervisor link in the same audited transaction, ending the active inherited relationship; reinstatement uses the assignment workflow. Database guards block suspending a supervising lawyer while active assistants remain and protect an individual workspace primary lawyer.
- `GET /api/workspaces/:workspaceId/lawyers/:lawyerMembershipId/assistants` — Firm Admin may inspect a firm assignment; a Lawyer can list only their own supervised assistants.
- `POST /api/workspaces/:workspaceId/assistants/:assistantMembershipId/supervisor` with `{ "supervisorMembershipId": "..." }` — Firm Admin manages any existing active/suspended assistant assignment in the firm. A Lawyer may assign a previously active but unassigned assistant only to themselves or reassign an assistant currently supervised by them. The selected supervisor is revalidated as an active Lawyer membership with a LawyerProfile in that exact workspace. For `INVITED` assistants, assignment prepares the supervisor link but leaves the membership inactive until invitation acceptance.

Membership management is restricted to an active Firm Admin in a firm workspace. This allows an admin to grant practice roles to other members, including another Firm Admin, but the actor cannot change their own role or membership status. Platform `SUPER_ADMIN` is not a workspace administrator and has no access to these routes unless it also has the independently required active Firm Admin membership. Individual-practice Lawyers can manage assistant assignments but cannot manage workspace roles/settings; adding/inviting the primary Lawyer and creating a primary LawyerProfile still requires the separate workspace-creation/onboarding workflow.

All membership and assignment mutations re-resolve actor authority from the verified session identity and current database records inside a serializable Prisma transaction, lock rows involved in the decision, update the membership, and insert a low-detail `SecurityAuditEvent` in the same transaction. Failed writes roll back their audit. Inputs never confer actor, tenant, or privilege authority. Cross-workspace IDs are rejected by scoped lookups and database composite foreign keys. The database supervisor relation is the only inherited relationship currently modeled: changing it immediately removes the previous supervisor relationship from these membership queries. There is no matter access cache or matter authorization system to revoke yet; any future materialized grants/cache must have explicit revocation on reassignment. Assistant supervision itself still grants no matter access.

The invitation workflow accepts only existing active identities; it does not create accounts or provide email verification, password setup, invitation delivery, or public registration. Matter-level authorization and API-level role/permission bootstrap for legal records still need product decisions and implementation.

### Audit and security hardening (Milestone 4, Phase 5)

Membership workspace reads and writes now carry the verified server-side session ID from `SessionAuthGuard`. The service locks and revalidates that exact unexpired, non-revoked session and active user inside a serializable transaction, then re-resolves permission against current workspace and membership rows. Session/user shared locks remain held through the operation so logout or account disable is ordered before or after the request; a stale guard result cannot authorize a later membership mutation. The transaction locks the actor membership and mutation target; assistant-supervisor database triggers remain the final invariant check for concurrent supervisor changes. Successful changes and their audit insert commit together. A conflict, constraint error, session revocation, audit failure, or serialization abort leaves neither a partial mutation nor a success audit. The guard's initial context remains a route admission check, not the write authority.

`AUTHZ_DENIED` events are written after permission denial and never turn a deny into an allow. They are best-effort when the audit database itself is unavailable; the guard warns without disclosing credentials or request bodies. The requested workspace identifier is intentionally omitted from denial records because it is caller-controlled and may not reference an existing workspace. Failed login attempts are similarly unattributed to a user and store only a low-detail reason. Successful login/session creation, logout/revocation, and membership changes persist their success audit inside the same transaction as the state change where the operation has a state change.

`SecurityAuditEvent` is append-only by application convention only: the current schema has no database trigger preventing direct `UPDATE` or `DELETE`, and the runtime database-role privileges have not been split from migration-owner privileges. Before production, use a separate least-privilege runtime database role that can insert and read audit events but cannot update/delete them, and define a controlled retention/export procedure. A database owner or migration credential can currently alter audit history. No migration was added in this phase because the repository does not yet provision separate runtime/migration roles and the existing isolated integration cleanup requires deleting its own test records.

Session verification now rechecks the exact session in workspace membership transactions and reads. The `/api/auth/me` endpoint authenticates at the conditional `lastSeenAt` session update; a request already past that point may finish if logout starts afterward, which is treated as an in-flight request ordered before logout. Any future cookie-authenticated write must carry the verified session ID into its own transaction and repeat the active-session and actor-authorization checks; a controller guard alone is insufficient. Workspace membership deactivation and workspace suspension are re-evaluated on each request. Matter-level permissions, ethical walls, confidential-content support access controls, and cached matter-grant revocation remain unimplemented and must deny access until designed.

The platform still has explicit onboarding prerequisites: invitation acceptance works only for existing active identities and email delivery/account verification/password setup are not configured; frontend authentication and onboarding are not integrated; and no matter-level access, ethical-wall, or confidential-content support-access policy has been implemented. Individual-practice lawyer and primary-profile provisioning is available through the authenticated backend endpoint described below. Pending memberships remain `INVITED`, and assistant supervision grants no matter access.

Authenticated permission denials are recorded as `AUTHZ_DENIED` audit events with the actor, permission identifier, and sanitized request ID. Caller-provided tenant IDs and request contents are not copied into these events. Unauthenticated requests stop before permission evaluation and are not written as actor-attributed authorization events. Cookie-authenticated membership mutations additionally require a trusted Origin; this does not replace a future CSRF token/Fetch Metadata strategy for broader routes.

The API validates `DATABASE_URL` at startup and Prisma connects on the first database operation. The existing health endpoint remains a liveness response and does not probe database readiness. Default automated auth tests use an in-memory fake Prisma provider and do not connect to any database. Optional persistence coverage uses `apps/api/.env.test.example` and the `test:integration` script; it refuses to connect unless `AUTH_TEST_DATABASE_URL` names exactly `jurismind_auth_test`. Apply checked-in migrations to that dedicated database before running the integration suite. Never point it at `jurismind_dev`.

### Secure invitations and onboarding (Milestone 4, Phase 6)

`POST /api/workspaces/:workspaceId/memberships` now creates a workspace invitation for an existing active identity with a password-backed account; it does not create an identity or grant access. Firm Admins with the membership-management permission may invite eligible practice roles. Lawyers with the assistant-assignment permission may invite assistants only, and the invited assistant is preassigned to that lawyer while remaining inactive. The recipient is bound to the normalized email on that account and must accept while authenticated as the same user. `POST /api/invitations/accept` requires a valid server-managed session and trusted Origin. It activates the existing `INVITED` membership only after checking that the invitation is pending, unexpired, for the authenticated identity, the workspace is active, and the role still matches the immutable invited role. Acceptance consumes the invitation and writes its success audit in the same serializable transaction. A same-recipient replay of an already accepted invitation confirms the committed workspace result without duplicating the mutation or audit, covering lost responses. Mismatched identities and invalid tokens receive safe generic errors. `POST /api/workspaces/:workspaceId/invitations/:invitationId/revoke` allows an authorized workspace membership manager to revoke a pending invitation. Replacing an outstanding invite revokes it and creates a new token atomically; only one pending invitation per recipient/workspace is allowed.

Invitation tokens contain 256 bits of cryptographic randomness; only a SHA-256 hash is stored. Assistant invitations remain inactive until a valid active lawyer with a profile in that workspace is assigned. That assignment may be prepared while the membership remains `INVITED`; acceptance then activates it atomically. An invited assistant is never granted access before acceptance, and assistant supervision still does not grant matter access. Individual-practice lawyer/profile provisioning and primary-lawyer invitations remain outside this workflow.

No email provider is configured. `InvitationDelivery` defines the delivery boundary, and current responses report `delivery: not_configured` rather than claiming an email was sent. For local development only, set `INVITATION_DEV_TOKEN_DELIVERY=true` with `NODE_ENV=development` to receive the raw token once in the invitation creation response. Startup validation rejects this setting in production and for non-boolean values. Do not enable it in shared or production environments. This is a development handoff only; configure and test a real provider before relying on invitation delivery. The authenticated existing-user-only acceptance path deliberately does not provide public account creation, password setup, verification, registration, or password reset.

Invitation success audits record the actor, workspace, invitation target, request ID, and role where relevant; tokens and request bodies are excluded. Expired invitations are marked and audited when acceptance is attempted. The `workspace_invitations` migration is additive and uses restrictive foreign keys, a hash uniqueness constraint, role/state checks, indexes, and a partial unique index for one pending invitation per workspace identity. Authorization still comes from server context and existing workspace permissions; Super Admin is not implicitly a workspace manager.

At the Phase 5 review, a fresh npm audit could not reach `registry.npmjs.org` (`ENOTFOUND`). The installed Prisma toolchain is version 7.10.0; `prisma@7.10.0` includes `@prisma/config@7.10.0` → `deepmerge-ts@7.1.5` and `mysql2@3.15.3` as CLI transitive dependencies. The previously reported four high-severity findings could not be revalidated for current advisory status or remediation. No forced downgrade or audit suppression was applied; rerun npm audit when registry access is available and review compatible upstream Prisma updates.

### Individual-practice provisioning (Milestone 4, Phase 7)

`POST /api/workspaces/individual-practice` requires a verified session, trusted Origin, a non-empty `Idempotency-Key`, and a JSON body containing only `{ "name": "..." }`. The user identity comes from the session; user IDs, roles, profile IDs, and platform privileges are rejected as extra input. A transaction rechecks and locks the active session/user, then creates an `INDIVIDUAL` workspace, the actor's active `LAWYER` membership, one primary `LawyerProfile`, and `INDIVIDUAL_PRACTICE_PROVISIONED` audit event atomically. The response contains only workspace, membership, and profile identifiers/status metadata. It creates neither a firm nor a platform role grant and does not grant matter access.

The idempotency key is scoped to the authenticated user and stored in the audit event's request ID; a SHA-256 fingerprint of the normalized workspace name detects payload changes without copying that name into audit metadata. PostgreSQL advisory transaction locking serializes the same user/key pair. A replay with the same workspace name returns the original safe result; reusing a key with a different name returns conflict. A distinct key creates a distinct individual practice, including under a concurrent request; product policy currently sets no per-user practice limit. Callers should reuse the same key for retries of one intended operation. No schema migration was needed: the existing deferred individual-workspace constraint trigger requires the active lawyer and primary profile to exist at commit.

The endpoint provisions workspace identity only. It does not implement public registration, frontend onboarding, matters, confidential-content access, or authorization policy for legal records. Practice access remains bounded by membership and existing API permission checks; platform Super Admin remains separate from practice membership.

### Frontend authentication and onboarding (Milestone 4, Phase 8)

The browser API client uses `NEXT_PUBLIC_API_BASE_URL` (local example: `http://localhost:4000/api`) and sends cookie credentials with `cache: no-store`. The frontend never reads or stores the HttpOnly session token. Run the API with `TRUSTED_ORIGINS=http://localhost:3000` for local web development; do not widen the API origin allowlist for convenience. Production must serve the web and API from a compatible same-site arrangement for the existing `SameSite=Lax` API cookie to accompany credentialed browser requests. A cross-site deployment requires an explicit cookie/CORS/CSRF architecture review.

The public `/` route stays outside authentication. Dashboard route-group pages use a client bootstrap to call `/api/auth/me` and `/api/workspaces` before rendering. With the current separately hosted API/cookie contract, Next.js cannot reliably validate the API host's HttpOnly cookie for server-rendered protected routes in every deployment topology. Therefore the client gate prevents UI flashes but is not a security boundary: every data operation remains protected by server guards, permissions, scoped service queries, and transaction-level session checks. API/network failure renders an error state and never becomes an authenticated state. Authenticated client data exists only in React memory and is cleared at logout or bootstrap failure.

`GET /api/workspaces` derives the current identity from the verified session and returns only active memberships in active workspaces, with safe metadata and the existing role-to-permission mapping. The workspace query parameter only selects the UI context; it creates no authority. Navigation currently exposes only the sample workspace overview, which requires `workspace:read:metadata`. Matters, clients, documents, billing, audit, and administration routes are not treated as authorized; no current permission grants matter access. `SUPER_ADMIN` remains a platform role and does not add workspace memberships or matter permissions.

Invitation links place the one-time token in a URL fragment (`/invitations/accept#token=...`). Browsers do not send fragments to Next.js, the API, or `Referer` headers. The page reads it into component memory and immediately removes the fragment from browser history; no query-string token links are accepted. For a signed-out recipient, the page remains open while sign-in occurs in a separate tab. A same-recipient API replay confirms an already committed acceptance after a lost response, without a second mutation or success audit. The route uses `Referrer-Policy: no-referrer`; do not add analytics or error reporting that captures the page URL or component state.

### Schema constraints and safe migration

- Memberships are unique per user/workspace; composite keys prevent supervisor and lawyer-profile references from crossing workspaces.
- Platform roles are granted separately; a partial unique index permits at most one non-revoked grant per user/role.
- PostgreSQL checks/triggers validate normalized emails, token-hash shape, timestamps, workspace/role compatibility, assistant supervision, and individual-workspace primary-lawyer invariants.
- Foreign keys use `RESTRICT` so deleting a user/workspace cannot silently cascade legal access or audit records.
- RLS is not enabled in this phase. If added, use a restricted application role and transaction-scoped context; RLS is defense in depth, not a replacement for API authorization.
- The first migration is additive and intended for an empty database. Inspect it and confirm the target before deploying to any existing database. Do not use `migrate reset` or `db push`.
- The second migration adds individual-workspace primary-lawyer enforcement and performs a safe, unambiguous-only backfill. It intentionally aborts for ambiguous or missing existing individual-workspace lawyer profiles; resolve those records explicitly before retrying.

Local PostgreSQL setup uses the root `docker-compose.yml` with a named persistent volume bound to loopback. Copy `apps/api/.env.example` to `apps/api/.env`, replace all placeholders with local-only values, and ensure `DATABASE_URL` matches the `POSTGRES_*` settings. URL-encode special characters in the database username/password. Then run:

```powershell
docker compose --env-file apps/api/.env up -d postgres
npm run db:validate --workspace=@jurismind/api
npm run db:generate --workspace=@jurismind/api
npm run db:migrate:deploy --workspace=@jurismind/api
```

`db:migrate:deploy` applies checked-in migrations without resetting the database. No default production credentials are supplied.

## Security and tenant model

Tenant identity must come from the authenticated server-side session and membership lookup, never from a caller-controlled tenant identifier. Every tenant-owned query and mutation must be scoped and authorized on the server. Uncertain access is denied. Validate and normalize all untrusted input at API boundaries, and avoid logging client, matter, document, billing, communication, password, or session data.

Future relational models should encode tenant ownership in keys and constraints so relationships cannot silently cross firms. PostgreSQL row-level security may provide defense in depth; it requires a restricted application role, transaction-scoped tenant context, and careful connection-pool behavior. It does not replace application authorization. Audit events should record security-relevant actions without copying privileged content. Matter-level permissions and ethical walls remain future requirements and are not implemented by this foundation.

Sessions should be server-managed, stored securely, and issued in appropriately scoped `HttpOnly`, `Secure`, and `SameSite` cookies. Passwords must use a suitable password hashing function. Never store plaintext passwords or commit credentials, private keys, tokens, or real environment files.

## Application boundaries

- `apps/web`: public pages, authenticated user interface, accessible reusable UI, and typed API client code. It must not own authorization decisions or secrets.
- `apps/api`: Nest modules for identity/access, firms/tenants, clients, matters, documents, billing, audit, and content as each is implemented. Controllers handle transport; services contain business logic; data access remains tenant-aware.
- `packages/*`: optional shared contracts or utilities with no server secrets and no accidental coupling between apps.
- `docs/`: architecture decisions, operational guidance, and security design as those decisions are made.

Prisma and PostgreSQL were introduced in Milestone 4, Phase 1 for identity/access foundations. Phase 2 adds a Prisma 7 PostgreSQL client service and authentication endpoints. Redis, queues, and object storage are deferred until a concrete requirement exists.

### Password recovery and authenticator MFA (Milestone 1.2)

Password reset links use 256-bit random bearer tokens, persist only SHA-256 hashes, expire after 30 minutes, and are single-use. A successful reset updates the Argon2id hash, consumes outstanding reset links and login challenges, revokes all existing sessions, and writes its success audit in one serializable transaction. The API responds generically for unknown and ineligible email addresses; requests use a minimum response-time floor, and gateway delivery is dispatched without waiting on its network latency. Reset delivery is isolated behind `PasswordResetDelivery`; no provider is configured by default. Configure `PASSWORD_RESET_EMAIL_ENDPOINT`, `PASSWORD_RESET_EMAIL_API_KEY`, and `PASSWORD_RESET_EMAIL_FROM` together for an HTTPS JSON gateway that accepts `{from,to,subject,text}` with Bearer authorization. Use a provider-specific adapter if the selected service requires another contract. Delivery errors are not logged with request content or secrets. **Production prerequisite:** delivery is currently in-process and not durable; add a database outbox or shared queue before relying on password resets in production, so a process restart cannot lose a message.

MFA uses RFC 6238 TOTP (SHA-1, six digits, 30-second period, one-step clock drift) plus ten random single-use recovery codes. MFA secrets are AES-256-GCM encrypted at rest; recovery-code values are HMAC-SHA-256 hashed. `MFA_ENCRYPTION_KEY` must be a unique base64-encoded 32-byte key. Keep it in a managed secret store, preferably backed by KMS, never in source control. Key rotation needs a deliberate decrypt/re-encrypt procedure with versioned envelopes; the current `v1` envelope does not implement automated key rotation. Back up the key separately from the database. Losing it makes enrolled secrets unusable.

For local browser QA, an optional in-memory reset sink is available only with `NODE_ENV=development`, `LOCAL_PASSWORD_RESET_SINK_ENABLED=true`, and a process-scoped `LOCAL_PASSWORD_RESET_SINK_KEY` of at least 32 bytes. It cannot be combined with the HTTPS provider and environment validation rejects it outside development. `POST /api/auth/dev/password-reset-sink/read` returns and drains captured messages only for loopback requests with the matching Bearer key and trusted Origin; it is disabled by default, has no durable storage, and should never be exposed through a public reverse proxy. The reset request still generates and persists the real one-time hashed token and normal reset completion still validates it. Run `apps/api/scripts/start-browser-auth.ps1` from PowerShell to verify `current_database()` is local `jurismind_dev`, generate persistent local encryption keys, and start the API. The script sets `INVITATION_DEV_TOKEN_DELIVERY=true` only for that API process so invited assistant accounts can be accepted in a local browser. The ignored reset-sink key file `.env.browser-test.local` is user-only; do not copy its value into source, logs, or chat.

Start the web app in a second PowerShell window from the repository root with `npm run dev --workspace @jurismind/web`; `apps/web/.env.local` must set `NEXT_PUBLIC_API_BASE_URL=http://localhost:4000/api`. Run the API with `apps/api/scripts/start-browser-auth.ps1` from a PowerShell window in `apps/api`. Browser runs use only local `jurismind_dev`; the script stops if the configured connection targets another database. Integration tests use only `jurismind_auth_test` via `AUTH_TEST_DATABASE_URL` and independently verify the database name before fixture writes.

Provision local accounts through their intended server paths: run `npx tsx scripts/bootstrap-super-admin.ts` from `apps/api` to create the first Platform Admin (interactive password entry is hidden; the script refuses if any active Super Admin already exists); create Firm Admin and Lawyer accounts at `/firm/register` and `/lawyer/register`; then have a Firm Admin invite an already registered account as an Assistant and accept the returned development invitation token. Assistant accounts remain invitation-only, and public registration never grants platform roles. Do not use the auth-test fixture scripts against `jurismind_dev`. For integration fixtures, `npm run fixture:acceptance` and `npm run fixture:acceptance:cleanup` operate only on explicitly configured local `jurismind_auth_test` connections and validate both database identities before writes. The synthetic browser-auth fixture commands have the same dedicated-test-database restriction.

The local browser launcher stores MFA and lawyer-credential encryption keys in the user-only ignored root file `.env.browser-keys.local` so encrypted development records remain readable after API restarts. Keep that file private and never copy its contents into source control, logs, or chat. Local browser-created registration accounts are ordinary `jurismind_dev` data, so use distinct test email addresses and remove only test records you have positively identified; do not run fixture cleanup commands against this database.

Enabling MFA requires an authenticated session, password reauthentication, and TOTP confirmation. Login creates only a five-minute, HttpOnly challenge cookie for enrolled users; a server session is issued only after TOTP or a recovery code succeeds. Recovery-code regeneration and disablement require password and a fresh TOTP. Disabling MFA revokes other active sessions while retaining the session used to perform the verified change. Resetting a password revokes all existing sessions and unconsumed login challenges but does not disable MFA or change its recovery codes. Reset and MFA transitions are origin-guarded and use `Cache-Control: no-store`; trusted Origin validation plus `SameSite=Lax` is the current CSRF mitigation, not a complete defense against every same-site or browser-policy threat. Reverse-proxy rate limiting is still required: the login limiter is process-local, and MFA challenge attempts are capped in the database at five per challenge.

### Platform user administration (Milestone 1.3)

`GET /api/platform-admin/users` provides bounded, offset-paginated account search and filters (`page` 1–10,000; `pageSize` 1–100; name/email search up to 100 characters; platform/practice role; account status; active workspace kind). `GET /api/platform-admin/users/:userId` returns account identity and workspace membership metadata. `PATCH /api/platform-admin/users/:userId/status` accepts only `{ "status": "ACTIVE" | "DISABLED" }` and requires a trusted Origin. All three routes require an authenticated session and the independently granted `SUPER_ADMIN` platform permission; practice roles and workspace membership never authorize platform-wide listing or mutation. Query and response data excludes password hashes, sessions, reset tokens, MFA secrets, and recovery codes. The UI's role gate is only a navigation aid; the API guards and transaction checks enforce access.

Disabling an account and revoking its active server sessions are committed with `PLATFORM_USER_STATUS_CHANGED` in one serializable transaction. A rolled-back audit write therefore rolls back the account change and session revocation. Reactivation does not restore revoked sessions or reinstate suspended/revoked practice memberships. The acting Super Admin cannot disable their own account. A Super Admin account is considered viable for the final-administrator safeguard when its user is active, has a password hash, and has an active Super Admin grant; a serializable transaction prevents concurrent requests from disabling the last such account. Denied self/last-admin changes receive `PLATFORM_USER_STATUS_CHANGE_DENIED` audit events. This phase does not grant or revoke platform roles, create users, or provide access to matter/client/document data. Role grants still require an out-of-band controlled provisioning process.

Frontend supports password-reset request/completion, login challenge including recovery-code entry, and an authenticated MFA settings page. The reset token is carried in a URL fragment and removed from browser history before submission. E2E browser coverage is not configured in this repository; API unit tests cover cryptographic primitives and API/PostgreSQL tests are required for persistence behavior. Never use these foundations to imply tenant isolation, matter authorization, ethical walls, or production legal-data readiness.

### Public website CMS foundation

`ContentEntry` is platform-owned content for blog articles and informational pages. Entries have normalized unique slugs, bounded title/summary/body/SEO fields, and `DRAFT`, `PUBLISHED`, or `ARCHIVED` lifecycle states. The body is plain text and rendered through React text nodes; CMS HTML is not interpreted. Management and preview routes require an active session and a separately granted platform `SUPER_ADMIN`, revalidated inside the mutation/read transaction. Publish, unpublish, archive, create, and edit success events share the database transaction with their content writes. Slug uniqueness is global across statuses so a hidden entry cannot collide with a published URL. Public reads select `PUBLISHED` rows only; unpublished preview is available only through the protected management route. Public URLs use `/insights/:slug` for either supported content type.

### Lawyer credential verification foundation (Milestone 1.3)

`LawyerProfile` remains the canonical professional profile and is reached only through an active `LAWYER` `PracticeMembership`. `LawyerCredentialSubmission` stores one immutable review attempt per submission, linked to the membership and workspace by a composite foreign key. `LawyerCredentialDocument` is scoped to the same submission/workspace/membership. One pending submission per lawyer membership is enforced by a partial unique index. Rejection allows a new history row; an approved profile cannot submit again through the current workflow. Platform `SUPER_ADMIN` grants authorize review independently of practice roles. Lawyers can read only their own submissions and documents; membership in the same firm does not reveal another lawyer's credentials.

The submission form accepts card-holder name, jurisdiction, and card identifier. The identifier is AES-256-GCM encrypted with `LAWYER_CREDENTIAL_ENCRYPTION_KEY`; list and lawyer views receive only its final four characters, while an authorized Super Admin sees the decrypted value in a submission detail. The key must be a unique base64-encoded 32-byte secret, held in a managed secret store in production. Back it up and plan key rotation; changing or losing it without decrypt/re-encrypt makes stored identifiers unreadable.

No object-storage provider exists in the repository. Development and test use a generated opaque key in a private `.private-document-storage` directory outside the Next.js static tree, with restrictive POSIX directory/file modes where supported. Production storage reads/writes fail closed until a private object-storage adapter, private bucket policy, encryption, retention, and malware-scanning policy are provisioned. The local backend is not a production substitute; Windows filesystem ACLs are inherited from the process account. A process crash between file write and database commit can leave an unreferenced private file, so production storage needs orphan reconciliation. Supported uploads are limited to PDF/JPEG/PNG, 10 MB, with MIME-to-magic-byte checks; downloads require an authenticated owner or Super Admin and are returned as `application/octet-stream` attachments with `nosniff` and `no-store`.

Submission metadata, document metadata, upload/submission audit events, and review decision audit events use the same database transaction. Review decisions lock the pending row and use a pending-only compare-and-set; stale decisions return conflict. Upload bytes are written before the database transaction and compensating deletion is attempted on transaction failure; this is not a cross-system atomic commit. Approval records an authorized platform review only. It does not establish legal authenticity, regulator status, or external bar membership verification. No legal matters or client records are exposed by this workflow.
